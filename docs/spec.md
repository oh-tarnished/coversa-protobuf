# Specification revisions

Which revisions of the COVESA specifications each version of this schema was
generated from, and what changed in the output when either moved.

## Two sources, pinned separately

The schema has two upstreams and they are not interchangeable:

| Pin | Upstream | Format | What it contributes |
|---|---|---|---|
| `vss` | [vehicle_signal_specification](https://github.com/COVESA/vehicle_signal_specification) | `.vspec` | the vehicle tree — every signal, unit, bound and allowed-value set |
| `vdm` | [vdm](https://github.com/COVESA/vdm) | GraphQL SDL | what COVESA models *outside* the vehicle — people, charging stations, sessions |

Both are git submodules under [`modules/`](../modules), which holds every
upstream checkout and nothing this repository writes. Each is pinned
separately in [`sync/spec.yaml`](../sync/spec.yaml), because each moves
separately.

VSS was not always read directly. The generator first took VDM's GraphQL
translation of it, which is lossy — 181 `comment` fields, most `default`
values, every `pattern` and every numbered enum are dropped in translation,
and names are damaged by case-splitting. See
[`decisions.md`](decisions.md).

Revisions are **dated, not numbered**, the way the Model Context Protocol
versions its specification. Neither upstream publishes release numbers a
reader could place — COVESA's `vdm` repository carries a single placeholder
tag, and VSS's tags do not track the branch this reads — so a number invented
here would mean nothing. A date is directly comparable against the source
history, and it sorts.

Both pins are stamped into every generated file's banner:

```proto
// Generated by sync from the COVESA Vehicle Signal Specification,
// revision 2026-09-02 (cd4bc50), and the
// Vehicle Data Model, revision 2026-07-24 (36bc939).
// DO NOT EDIT.
```

That stamp is the point of dating them. "Which specifications is this schema
from?" is answerable from any single `.proto` a consumer happens to be
holding, without access to this repository's git history.

## Two submodules, and the other two COVESA specifications are not among them

COVESA publishes three repositories with `spec` in the name. Only one of them
is a source this generator can read.

| Repository | What it holds | Here |
|---|---|---|
| `vehicle_signal_specification` | the vehicle tree, in `.vspec` | submodule `vss` |
| `vehicle-information-service-specification` | VISS, an access protocol, as HTML prose | no |
| `commercial-vehicle-information-specifications` | CVIS, `.vspec` trees for bus, truck and trailer | not yet |

`vdm` is the second submodule and matches none of those searches, because
what it contributes is not a specification of the vehicle: it is the GraphQL
SDL for what COVESA models *outside* it -- people, charging stations,
sessions. Two submodules, two different jobs, neither substitutable for the
other.

**VISS is not a data model.** `spec/` is three HTML documents describing how a
client reads and writes VSS data over HTTP and WebSocket -- request framing,
subscriptions, payload encoding. It defines no types. It is a *consumer* of
VSS, in the same position as this repository, and vendoring it would give the
generator nothing to parse. It belongs in `references.md`, which is where it
is.

**CVIS is a real `.vspec` corpus, and still cannot be added as it stands.**
`spec/trees/` holds root files for Bus, Truck, Trailer and Driver in exactly
the format `sync/vspec` already parses. Three things block it:

- It vendors its own `Vehicle/Car/VehicleSignalSpecification.vspec`, a fork of
  the upstream root that has fallen behind it -- no `ElectricMotor`
  instances, no `RangeExtender`, no `Safety`, and an `OBD` branch upstream no
  longer has there. Adding it produces two `Vehicle` trees of different
  vintages, and nothing in the pipeline would report which one a message came
  from.
- Its trees are not readable on their own. A truck is the car tree plus an
  overlay that `vspecPreprocessor.py` generates from a JSON configuration;
  the `.vspec` files without that step describe no particular vehicle.
  `sync` has no overlay support, and rule 15 says it refuses rather than
  guesses.
- It is `0.1-dev`, with no dated release a pin could name -- and rule 9 wants
  a revision a consumer can place.

When it is taken, it is taken as a fourth `<spec>` segment --
`protobuf/covesa/cvis/...` -- reading the Bus, Truck and Trailer roots only,
with the Car fork ignored in favour of the pinned VSS one. Not as a
replacement for `vss`.

## Bumping a pin

A pin is not a version this repository chooses; it records what was read.
Moving one is four steps, and the middle two are not optional:

```sh
git -C modules/vss pull          # 1. move the specification checkout
$EDITOR sync/spec.yaml           # 2. set version and commit to match
just sync                        # 3. regenerate every proto, README and the manifest
just ci                          # 4. every gate, including the schema layers
```

Then record what moved in the history table above — new resources, renamed
fields, anything a consumer would have to react to.

`just spec` (and CI) checks both pins against their checkouts: that each
commit is the one checked out, that each version is that commit's date, and
that each tree is clean so the commit describes it fully. Without that check a
stale pin would put a revision into 270 banners that the files were never
generated from — a claim no linter and no compiler can see is false.

## What a bump can break

A specification bump is a **breaking-change review**, not a routine update.
`buf breaking` runs on every pull request and will catch a removed or
renumbered field, but four things it cannot see are worth checking by hand.
The first three are reported by `just survey`; the fourth is a build error.

- **New AIP collisions.** A new signal name may trip a rule no existing field
  does. `just survey` reports every trap and how many are resolved; an
  unresolved one is listed with what to do about it. The resolution goes in
  `catalog.FieldRenames` — or, where the name is right as it stands, in
  `catalog.AcceptedTraps` with the reason — and a matching row goes in the
  catalogue at the foot of [`conventions.md`](conventions.md).
- **New top-level branches.** A branch the `domains` table does not name lands
  in `platform` and is reported rather than silently filed. Give it a real
  domain. `Orientation` and `Safety` both arrived this way.
- **A newly ambiguous name.** VSS names a branch for what it is, not where it
  sits, so a new `Axle` somewhere else in the tree makes three packages into
  four. `model.disambiguate` qualifies each by as much of its path as it
  takes, which *renames* the existing ones — a breaking change caused by an
  unrelated addition. `buf breaking` catches it; the survey shows it first.
- **A stale rename.** A signal removed upstream leaves its catalogue entry
  resolving nothing, and the rename is then simply never applied — valid
  output, every linter passing, a decision recorded about a field that no
  longer exists. `model.CheckCatalogue` makes it a build error naming each
  one.
- **Moved field slots.** A field removed upstream without a `reserved` in its
  place shifts every FlatBuffers and Cap'n Proto slot after it. `buffers.lock`
  is the record that this has not happened, and CI fails on a change to it.

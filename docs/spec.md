# Specification revisions

Which revision of the COVESA Vehicle Data Model each version of this schema
was generated from, and what changed in the output when it moved.

Revisions are **dated, not numbered**, the way the Model Context Protocol
versions its specification. The upstream model publishes no release numbers —
COVESA's `vdm` repository carries a single placeholder tag and nothing else —
so a number invented here would mean nothing to a reader. A date is directly
comparable against the source repository's history, and it sorts.

The current pin lives in [`sync/spec.yaml`](../sync/spec.yaml) and is stamped
into every generated file's banner:

```proto
// Generated by sync from the COVESA Vehicle Data Model,
// spec revision 2026-07-24 (36bc939). DO NOT EDIT.
```

That stamp is the point of dating it. "Which specification is this schema
from?" is answerable from any single `.proto` a consumer happens to be
holding, without access to this repository's git history.

## Bumping the pin

The pin is not a version this repository chooses; it records what was read.
Moving it is four steps, and the middle two are not optional:

```sh
git -C vdm pull                  # 1. move the specification checkout
$EDITOR sync/spec.yaml           # 2. set version and commit to match
just sync                        # 3. regenerate all 276 protos
just ci                          # 4. every gate, including the new schema
```

Then record what moved in the history table above — new resources, renamed
fields, anything a consumer would have to react to.

`just spec` (and CI) checks the pin against the `vdm` working tree: that the
commit is the one checked out, that the version is that commit's date, and
that the tree is clean so the commit describes it fully. Without that check a
stale pin would put a revision into 276 banners that the files were never
generated from — a claim no linter and no compiler can see is false.

## What a bump can break

A specification bump is a **breaking-change review**, not a routine update.
`buf breaking` runs on every pull request and will catch a removed or
renumbered field, but three things it cannot see are worth checking by hand:

- **New AIP collisions.** A new signal name may trip a rule no existing field
  does. `just survey` reports every field name that hits a known trap; the
  resolution goes in `fieldRenames`, and a matching row goes in the catalogue
  at the foot of [`conventions.md`](conventions.md).
- **New top-level branches.** A branch the `domains` table does not name lands
  in `platform` and is reported rather than silently filed. Give it a real
  domain.
- **Moved field slots.** A field removed upstream without a `reserved` in its
  place shifts every FlatBuffers and Cap'n Proto slot after it. `buffers.lock`
  is the record that this has not happened, and CI fails on a change to it.
